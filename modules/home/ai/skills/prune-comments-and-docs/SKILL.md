# Prune Comments and Docs

コメントと文書は、コードから導けない情報だけを残す。読者がコードと文書のどちらも信頼できる状態にするのが目的である。

判断基準は pstack の no-comments / Comment Sicko を下敷きにし、文書へ拡張した。keep list に当てはまらないものは削る。コメントも文書も迷ったら削る。文書はコードや git から得られない情報を持つ場合だけ残し、残した理由を報告する。

`MUST KILL` は、コメントを削ったうえで、対象シンボルをコメントなしで意図が分かる形に直す必須項目である。自コードの非自明な挙動はコメントで説明せず、`MUST KILL` として扱う。

## 対象と除外

対象は次を含む。

- コードの行コメント、ブロックコメント
- docstring、JSDoc、GoDoc などの API コメント
- README、docs/ 配下、設計メモ、ADR、CONTRIBUTING
- 設定ファイルやスクリプト内のコメント

次は編集しない。

- 生成物、vendored code、lockfile
- ライセンス全文、第三者由来の表記
- テストの assertion message やログ文字列。削除対象にせず、コメントの代わりに使う。

## 残す基準

コメントで残すのは次の 4 種類だけである。

1. ライセンス・著作権表示、ツールが要求する directive（`prettier-ignore`、生成物マーカーなど）
2. 公開 API の契約を定義する doc comment。ただし型で表せない制約に限る。単位、値の範囲、null の意味、副作用、送出するエラー、スレッド安全性など。引数名や型の言い換えは残さない。
3. 外部依存、プラットフォーム、プロトコル、ベンダーの仕様に強制され、こちらで変更できない非自明な挙動。参照先を添える。自コードの非自明な挙動はここに含めない。
4. コードでは表現できない制約を説明する issue / RFC / 仕様へのリンク。

文書で残すのは次の 3 種類である。

5. コードを読まない利用者が作業を完了するために必要な契約と手順。インストール、初回起動、使い方、公開 API リファレンス、移行手順、運用 runbook、セキュリティやコンプライアンスの要件。コードや `--help` から再構成できる説明は含めない。
6. コードと git から再構成できない設計判断。なぜその構造にしたか、どの代替案を捨てたか、外部から課された制約。現在の設計を拘束している ADR を含む。
7. 上記を検証する実行可能な例。テストやサンプルとして保守されているもの。

## 削る基準

- 実装の言い換え。関数名の復唱、`// if`、`// return`、`// 1. ...` のような段階バナー、処理の逐次説明。
- コメントアウトされたコード、使われない分岐、後で使うかもしれない死んだ実装。
- 変更履歴。いつ誰が何を変えたか、以前はこうだったという説明。git にある。
- 所有者もチケットもない TODO / FIXME。現在の制約を書いているなら、制約をコード・型・テスト・lint に移してから消す。
- 型が既に表している引数・戻り値の説明。
- `IMPORTANT`、`do not remove`、`too risky`、`fine for now` と長い正当化。名前付きのシンボルや依存先をたどり、現在も成り立つ証拠を確認する。証拠があっても keep の番号に当てはまらなければ削る。
- 自コードの非自明な挙動を説明するコメント。`MUST KILL` とし、rename、extract、型やテストの追加で自明にする対象を名指しする。
- 削除した内容を短く言い換えたコメント。同じ情報を残す抜け道になる。
- コードを複製した文書。ファイルツリー、型やエンドポイントの一覧、コードから生成できる表、重複した quickstart、意思決定のない overview、AI が書いた要約。
- 完了済みの計画、仕様、チェックリスト。現在の挙動を拘束していないなら削る。必要な履歴は issue か git に委ねる。
- 正しさや安全性を守っている lint / 型 suppression は、ルールを確認する。ルールが正しいなら抑制を外し、該当シンボルを最小限直す。直せない場合も keep には数えず、未解決の `MUST KILL` として対象シンボルと修正案を報告する。ルール自体が誤りか style-only の場合だけ残す。
- 複数箇所に重複した文書。正となる 1 箇所を決めて残し、他を削る。削除前に index とリンクを確認する。

## 手順

1. 範囲を決める。既定は base branch（main）との差分と未追跡ファイル。ユーザーがパスを指定したらその範囲に従う。コードを書いた直後なら、サブエージェントなど、変更を書いていない別コンテキストの reviewer に判定させる。それができない場合は、書いた本人とは別のパスで読み直し、keep ごとに外部要因の証明を書く。
2. 範囲内のコメントと文書を列挙し、周辺のコードとテストを読んでから判定する。
3. keep / delete / `MUST KILL` に分類する。keep には適用した基準の番号を、delete には何が同じ情報を持っているかを対応付ける。`MUST KILL` には対象シンボルと修正案を対応付ける。
4. keep 候補の主張を検証する。`do not remove` や外部制約は、シンボル、依存先の仕様、issue をたどる。証拠があっても keep の番号に当てはまらなければ削る。自コードの非自明な挙動は keep にせず、`MUST KILL` として扱う。
5. 削除する。`MUST KILL` の修正が小さく範囲内なら、rename、不要な引数の削除、実 API の使用、型やテストの追加で根本原因を直す。範囲外ならコメントだけ削り、対象シンボルと修正案を報告する。
6. 制約コメントは、型、実行時チェック、テスト、lint のうち最も安い手段で表現してから削る。表現が範囲外なら、制約を未表現として報告する。
7. 検証する。build、test、lint を実行する。文書を削った場合は、README、docs index、package metadata、CI、Web サイトからのリンクを確認する。公開 API の doc 生成があるなら生成も確認する。
8. 報告する。ファイルごとの削除数、残した項目、適用した基準、外部要因の証明、`MUST KILL` の対象シンボルと修正案、未表現の制約、実行した検証を書く。

## 文書を削るときの追加確認

- 外部の利用者が契約として読む文書ではないか。公開 API、CLI フラグ、設定キー、ファイル形式、移行手順は削除で利用者を壊す。
- 削除後に同じ情報がコード、型、テスト、`--help`、生成物から得られるか。
- 情報が古いだけなら、削除ではなく更新を選ぶ。移設すべきなら 1 箇所に移し、元を消す。
- 削除した内容を要約して別の場所に書き直さない。重複の再生産になる。

## やらないこと

- 公開 API の契約、ライセンス表記、運用手順を「コメント削減」の名目で消さない。
- 生成物、vendored code、lockfile を編集しない。
- 削除のついでにコードの挙動を変えるリファクタを広げない。
- 判断に迷ったコメントを残さない。keep の番号に当てはまらないものは、証拠があっても削る。
- 判断に迷った文書は削る。例外は、公開 API、CLI フラグ、設定キー、ファイル形式、移行手順など、外部の利用者が契約として読む可能性がある場合である。その場合も keep として受理せず、削除せず未解決として報告する。
